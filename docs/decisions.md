## Phase 1 — additional decisions

- **`settings` row provisioning.** Nothing in the spec says how a user's `settings` row comes to exist (there's no sign-up flow to attach it to). A Postgres trigger on `auth.users` insert (`handle_new_user`) seeds one default `settings` row (`pnl_convention='kr'`, `default_instrument='EURUSD'`, `default_session='asia'`, `r_precision=1` — `locale` was part of this row too until it was dropped, see the Phase 3 follow-up entry below). `accounts` are **not** auto-seeded the same way — starting capital, currency, and risk mode need real user input, so the first account is created through onboarding UI (Phase 8), not a trigger default.
- **`session` default.** README doesn't state one; picked `asia` (the first session of the trading day) as `default_session`'s seed value. Easy to change in Settings once that screen exists.
- **`r_precision` default.** Not specified; seeded at `1` (one decimal place on R values, matching every R value shown in the mocks, e.g. "+18.4R").
- **Storage bucket RLS.** `chart-shots` is private; objects are scoped by putting the owning user's id as the first path segment (`{user_id}/{trade_id}/{filename}`) and writing storage RLS policies against `auth.uid()::text = (storage.foldername(name))[1]` — the standard Supabase per-user-folder pattern, since `storage.objects` has no `user_id` column of its own to key RLS on directly.
- **`CHECK` constraints, not native Postgres enums, for `direction` / `session` / `htf_pairing` / `result` / etc.** Keeps future value changes a plain migration (`ALTER TABLE ... DROP/ADD CONSTRAINT`) instead of `ALTER TYPE` ceremony (which can't drop values). Trade-off: `supabase gen types` can only narrow to a literal union from a real Postgres enum, so these columns come back as plain `string` in `database.types.ts`. Tighter literal-union types + zod schemas for these fields belong in `src/lib/domain/` once that lands in Phase 2 — the generated file is intentionally the loose, raw-schema layer, not the app-facing one.
- **Migrations validated locally before handoff.** Ran `pnpm exec supabase start` (local Docker Postgres + auth + storage) once, applied all four migrations against it end to end with no errors, generated `src/lib/database.types.ts` from that local instance, then `supabase stop`.
- **Login screen has no mockup** (`docs/README.md` § Routes lists `/login` with none). Built plain with tokens directly rather than Button/Input primitives, since Phase 3 (design system) hadn't landed yet. **Refactored onto `Field`/`Input`/`Button` at the end of Phase 3**, as flagged here.
- **Bug found + fixed: `loginSchema` couldn't be exported from `actions.ts`.** That file is `"use server"`, which only supports async-function exports (server actions) — re-exporting the zod schema object from it corrupted the object across the server/client bundle boundary, and `zodResolver` threw `Invalid input: not a Zod schema` at runtime. Moved `loginSchema`/`LoginInput` into `src/app/login/schema.ts` (no `"use server"`), imported by both `actions.ts` and `login-form.tsx`. Caught by actually loading `/login` in a browser, not by `pnpm build` (Next's prerendering never executes the client component's `zodResolver()` call, so the build stayed green through this).

## Phase 1 — bug found by opening `/login` in a real browser: Tailwind spacing was 4x too large everywhere

The user reported `/login` rendering broken — tall narrow card, square inputs, a button that didn't stretch, system font instead of Pretendard. `pnpm build`/`lint`/`test` were all green throughout; none of them would have caught this.

- **Root cause:** Tailwind's default `--spacing` base unit is `0.25rem` (4px) — bare numeric spacing utilities (`p-32`, `gap-16`, `w-32`, `px-16`, ...) compute to `N * 4px`, not `N px`. Every spacing value in `docs/README.md`'s Design Tokens is already a literal px number, and every component written so far (`/login`, `/dev/tokens`, `/`) used those numbers directly as Tailwind class suffixes (e.g. `p-32` meaning "32px"), assuming a 1:1 mapping that Tailwind does not use. Confirmed in a real browser via computed styles: `p-32` on the login card computed to `padding: 128px`, not `32px` — 4x over, exactly matching the multiplier.
- **Why colors/radius/font-size looked fine:** those come from custom `@theme` keys with fixed, explicit px values (`--radius-24: 24px`, `--text-56: 56px`, ...), not from Tailwind's dynamic spacing-multiplier scale — only the spacing-derived utilities (padding/margin/gap/width/height/inset) were affected.
- **The font was not actually broken** — `document.fonts` showed `"Pretendard Variable"` loaded and applied on every element checked. The 4x spacing bug made the layout collapse enough that Pretendard's fairly plain Latin letterforms read as a generic system font at a glance; there was no separate font-loading bug to fix.
- **Fix:** redefined `--spacing: 1px` inside the `@theme` block in `globals.css`, rather than rewriting every call site to the `N/4` form (verified first that the codebase has zero existing usages of Tailwind's fractional spacing convention like `p-1.5`/`gap-2.5`, so there was nothing to conflict with). One-line change, fixes every page at once.
- **Verified the fix in a real browser, not just a rebuild:** re-inspected computed styles on `/login` (card padding now `32px`, email input width now `316px` = 380 − 2×32, button padding `17px`), then logged into `/dev/tokens` and `/` with a second disposable test user (created and deleted the same way as the Phase 1 login test) and visually confirmed every section — colors, type scale, radius swatches, spacing bars — renders correctly, not just the one page that was reported broken.
- Fixed a stale, now-wrong claim in `/dev/tokens`'s own copy ("Tailwind default scale — 4px base already matches") to describe the actual `--spacing: 1px` override instead.

## Phase 2 — domain logic

Four rules the spec left open, put to the user and confirmed before implementing:

- **Break-even R.** `result` is a label, never an input to the R maths: `realizedR` always comes from the actual exit, so a 'be' trade lands at ~0.0R on its own instead of being forced to exactly 0. Keeps `pnlAmount` (and therefore the balance series) reconcilable with the real account when a "break even" exit was a few ticks off. **No exit → `realizedR` is `null`, not 0**, and such trades are skipped by the aggregates rather than counted as zeros (counting them would quietly drag net R and expectancy toward zero).
- **Break-even in the aggregates.** Win rate = wins / trades-with-a-result, so BE sits in the denominator only — mock 2c prints "67%" with the sub-line "6 / 9", i.e. the denominator is the trade count. Avg win / avg loss exclude BE entirely. Expectancy includes it (a scratch really does dilute expectancy). **Win streaks treat BE as neutral** — it neither extends nor breaks a run, it is skipped; only a loss resets. A trade with no result yet is skipped the same way.
- **Mid-range band = `MID_RANGE_HALF_BAND` (0.10), i.e. 40%–60%.** Symmetric around the 50% equilibrium line, the only range level `docs/README.md` actually draws. Sanity check: the one trade the canvas chips "On plan" (mock 2b) has its entry at 9.9% of the range, far outside the band. Kept as a named constant so it can move into Settings later.
- **`offPlan` is trade-local: `sweepSide === 'none' || entryIsMidRange`.** Model retirement is deliberately *not* an input. `offPlan` is recomputed on every read, so including model status would retroactively flip already-logged trades to off-plan the moment a model is retired — silently rewriting history and moving past adherence numbers, which a trading journal must never do. README §Playbook ("retiring ... marks future matches off-plan") and the retired model's mock description ("new entries are flagged off-plan") are therefore read as applying **only to trades recorded after the retirement**, honoured as a warning in the trade form at log time. The mock stays consistent either way: its 8 off-plan trades all belong to the retired "Mid-range entry" model, whose own description is "No sweep, no confirmation" — so they are already off-plan via `sweepSide === 'none'`.
- **Rule adherence = (trades − off-plan trades) / trades**, over every trade in the period (BE included), reading the derived `offPlan` flag — *not* the manual "On plan" tag, which is a separate self-assessment tag sharing a row with Impatient / Chased entry / Early exit. Not a judgement call: reverse-engineered from two independent mocks and confirmed. Weekly 2c shows 89% with "1 off-plan" over a 9-trade week ((9−1)/9 = 88.9%); dashboard 1a shows 87% over 61 trades (24+18+11+8, matching "View all 61") of which the 8 "Mid-range entry" ones are flagged ((61−8)/61 = 86.9%). Both are locked in as regression tests.
- **Time-weighted return is chain-linked.** The timeline is cut into sub-periods at every cash movement; each sub-period returns (trading P&L / balance at the start of that sub-period); the factors are multiplied. Sub-periods starting at a balance ≤ 0 are skipped rather than dividing by zero; no trades at all → 0%. **Mock 3a's "Return on capital +43.0%" is not a TWR** — it is the same number as the "+43.0R lifetime" printed beside it, i.e. the plain sum of R at 1% risk, and was judged to be the mock author reusing the R figure rather than specifying the maths. We compute the real thing, which is what README's own "time-weighted, so deposits don't inflate it" asks for. Covered by a test where TWR is 21% while the naive money-weighted view would read 15.5%.

Smaller calls made while implementing, none of them spec'd:

- **Same-date event ordering: cash movements before trades**, `createdAt` as the final tiebreak — a deposit dated D funds that day's trading. Makes the balance series, the TWR sub-periods, and the ledger's running-balance column all deterministic.
- **"Win streak" is ambiguous in the mock** (dashboard shows "4 trades" with no sub-line, so it could be the current run or the best one). `winStreaks` returns **both** `longest` and `current` rather than guessing. **The dashboard shows `current`** — decided by the user: a streak is a read on the state you are in right now, not a personal-best record. `longest` stays on the selector (it costs nothing and the weekly review may want it) but is not on any screen.
- **Selectors return raw ratios (0..1), never pre-rounded percentages.** Display rounding (adherence to a whole %, R to `settings.r_precision`) belongs to the UI, so one selector can feed both a stat card and a chart. Tests assert both the raw value and the rounded one the mock shows.
- **Domain types are camelCase and carry real literal unions**, bridging the loose generated `database.types.ts` (where CHECK-constrained columns are plain `string`). The row → domain mapper lands with the queries in Phase 4.
- **Dates are compared as `YYYY-MM-DD` strings**, never `Date` objects — lexicographic order is chronological order and there is no timezone to get wrong.
- **Currency is left at full float precision in the domain**; rounding is display-only. Tests compare money to the cent (`toBeCloseTo(x, 2)`) since e.g. 9.68R × $1,000 lands on 9680.000000000002.
- **Drawdown warning margin is 2 *percentage points*** (`DRAWDOWN_WARNING_MARGIN_PCT`), so a 10% limit starts warning at 8% drawdown — the natural reading of README's "within 2% of the limit". Cross-checked against the mock: peak $32,180 with a −10% limit gives "Stop trading at −$3,218".
- **Mock 2b's "93% captured" is a rounding artifact**, like the 43.0% above: 2.8103R / 3.0R is 93.7%. Both displayed numbers in the mock are themselves rounded, so there is no real conflict — `captureRate` computes from raw values.

## Phase 3 — design system primitives

- **`clsx` + `tailwind-merge` added.** Not a component kit (the build prompt bars those) — they are the class-merging utility that lets a caller's `className` actually override a component default, which plain string concatenation cannot do (CSS source order decides, not string order).
- **tailwind-merge had to be taught this project's scales, and silently corrupted components until it was.** Our type scale is keyed by px number (`text-13`, `text-11_5`), which collides with Tailwind's text-*colour* namespace: out of the box tailwind-merge classified `text-13` as a colour and dropped the earlier `text-white`, so the `ink` button rendered as **black text on a black fill**. The px-named radius scale had the same problem in reverse (`rounded-24` and `rounded-8` never deduped). `src/lib/cn.ts` now extends the merge config with both scales. Caught by looking at `/dev/components` in a browser — `pnpm build`, `lint`, and `tsc` were all green with the bug in place, which is the same shape of failure as the Phase 1 zodResolver bug and the Phase 2 spacing bug.
- **The capital chart's 1R line gets its own vertical band** (viewBox y 62%–89%, matching the mock's 106–152 of 170) rather than being stretched over the full height. 1R is a fixed percentage of the balance, so on a full-height "own scale" it normalises to the *exact same shape* as the balance line and disappears underneath it — which is precisely what happened on first render. Confirmed against the mock rendered in a browser, where the 1R line clearly sits lower and flatter than the balance line.
- **`BottomTabBar` is designed, not mocked.** The 1d mobile mock has no tab bar (its home screen ends at the "기록하기" CTA), but the build prompt requires one for mobile nav. Built from the TopBar's vocabulary — active takes ink, inactive stays muted — with every target over the 44px minimum and `env(safe-area-inset-bottom)` padding.
- **`RangeDiagram` is built with divs, in Phase 3**, per the build prompt's note that it is layout rather than a chart. Vertical position is price (top edge = range high, bottom = range low, hairline = 50% equilibrium); horizontal offsets are reading order only and match the mock's. The "Sweep" label landing on the same line as the caption row was checked against the canvas rendered in a browser — the mock does the same thing, so it is faithful rather than a bug.
- **`EmptyState` is designed, not mocked**, as docs/README.md § Empty states asks: the card vocabulary at rest, a 700 16px title over a 500 13.5px line, with one optional action.
- **Charts reproduce the mocks' `preserveAspectRatio="none"`**, so strokes stretch horizontally with the container exactly as the mock does. That is deliberate fidelity, not an oversight.

### 1. "Recent trades" tiles truncating

Fixed by splitting the mislabeled block into two accurate, correctly-scoped demos:

- **"Result info tiles"** — the real `220px 1fr` split with `repeat(4,1fr)` tiles, at full card width. No truncation at any size checked (verified via `scrollWidth`/`clientWidth` in the browser, not eyeballed).

### 2. Letter-spacing / line-height / gaps reading wider than the mock

Three real, verified discrepancies, all against a spec that turned out to have more variants than the primitives modeled:

- **StatCard had an invented 28px size that doesn't exist in README's own type scale.** The canvas mock does use 28px in one place (Capital's 4-up row), but `docs/README.md`'s Design Tokens § Typography lists the scale explicitly and 28 is not in it (11/11.5/12/.../26/30/44/56). Per `docs/build-prompt.md` §1's rule ("README와 캔버스가 충돌하면 README를 따르고"), rounded Capital's stat cards to the 30px family used everywhere else (dashboard, weekly review) rather than adding a one-screen-only size. Also found: **the calendar summary row's 26px values carry no letter-spacing at all** in the canvas markup, while every 28px+ value explicitly sets `-0.03em` — an intentional-looking distinction, not an oversight, so `StatCard` now has exactly two variants (`sm`: 26px, no tracking; `lg`: 30px, `-.03em`) instead of one shared tracking class.
- **`BarRow`'s caption line used `margin-top:8px`; the mock uses 6px.** The bar's own margin-top does equal its track height (8px for an 8px track, 7px for a 7px track — that part was already right), but the caption below it is a separate, smaller gap. Also found the 7px-track variant (weekly tag frequency) uses a **13.5px label**, not 14px — the two track heights are genuinely different components sharing a shape, not one component at two sizes. `BarRow` now branches its label size and bar margin off `height`, with the caption fixed at 6px regardless.
- **The CRT-sequence chip row (trade detail) uses a 10px gap; the emotion-tag row (new trade form) uses 8px.** The gallery had both using 8px, having conflated two visually similar but differently-specified pill rows. Demo split to show both gaps explicitly rather than picking one.

### 5. Language is decided by viewport width, not `settings.locale`

Confirmed rule: **≥900px → English** (matches the responsive breakpoint already used for layout — docs/README.md's own `<900px` language), reading the PC mocks (1a-1c, 2a-2d, 3a); **<900px → Korean**, reading the 1d / 3b-mobile mocks. Reasoning given: mobile is for logging a trade in the moment (native language reads faster under time pressure), desktop is for analysis (trading terms read more naturally in English, which is also what every PC mock is authored in). Not a user setting — the same one responsive codebase now branches copy the same way it already branches layout, with no `/mobile` route.

**Mechanism — `src/lib/i18n/` (`locale.ts` + `locale-context.tsx`):**

- `getViewportLocale(width)` is the single source of truth for the breakpoint (900px, `LOCALE_BREAKPOINT_PX`, deliberately identical to the layout breakpoint already in the responsive rules — one number, not two that could drift apart).
- **No-flicker strategy, and why it doesn't need a blocking `<head>` script:** the classic "avoid flash" pattern (à la `next-themes` for dark mode) uses a blocking inline script to mutate the DOM before React ever mounts, because that trick is for a CSS class toggle — trivial vanilla-JS DOM work with nothing to reconcile. This is different: the payload is *text content*, which has to go through React's tree regardless (there is no CSS-only way to swap arbitrary Korean/English strings without rendering both languages into the DOM at once, which does not scale as the app's i18n mechanism for every future screen's copy — see the tradeoff note below). So instead:
  1. **`RootLayout` (Server Component) reads the `viewport-locale` cookie** (`cookies()`, Next 15's async API) and renders `<html lang>` and the `LocaleProvider`'s starting state from it. Once a visitor has been here before, this is correct from the very first byte the server sends — no client correction ever runs.
  2. The **only** time the guess can be wrong is a visitor's first-ever request, when no cookie exists yet — the server then defaults to `"en"`. `LocaleProvider` initializes its React state to that exact server-provided value (required: the client's first render must match the server's or React throws a hydration-mismatch error), then in a **`useLayoutEffect`** — which fires synchronously after the DOM commits but strictly *before the browser paints* — measures the real `window.innerWidth` and corrects the state if it disagrees, and writes the cookie for every future visit. Because this runs before paint, the correction is invisible; there is nothing to see flash.
  3. That same effect attaches a `matchMedia('(min-width: 900px)')` listener, so live resizing across the breakpoint (a desktop window resize, a tablet rotation) updates the locale immediately with no reload.
  - **Verified live in a browser**, not just read from the code: resized an actual window from 1400px to 700px and back. At 700px, `document.cookie` showed `viewport-locale=ko`, `document.documentElement.lang` was `"ko"`, and both `TopBar`'s and `BottomTabBar`'s nav labels (pulled from the *same* shared dictionary via `t()`) switched to Korean live, with no reload; resizing back to 1400px flipped both back to English live. (This sandbox's browser window doesn't let its CSS viewport track `resize_window` reliably — the first couple of attempts read back the old width — so this was confirmed by re-reading `window.innerWidth` after the resize each time until it actually reflected the new size, not by trusting the resize call alone.)
- **A real bug this caught that `pnpm build`/`lint`/`tsc` all missed**, the same shape as the Phase 1 `zodResolver` bug and the Phase 3 `tailwind-merge` bug: `parseInitialLocale` was originally defined in `locale-context.tsx`, which is a `"use client"` module. Next's RSC compiler does not allow a Server Component to call a plain function imported from a `"use client"` file directly (only render it as a Component, or pass it down as a prop) — `RootLayout` calling it threw `Attempted to call parseInitialLocale() from the server` at request time, a 500 on every single route, invisible to any static check because the type signatures are fine and nothing about it is wrong until it actually executes on a real request. Fixed by moving the function into `locale.ts` (no `"use client"`), which is safely importable from both sides.
- **Side effect: every route is now dynamically rendered** (`ƒ` instead of `○` in the build output), because `RootLayout` calling `cookies()` opts the whole tree out of static generation. Judged a non-issue here: `src/lib/supabase/server.ts`'s `createClient()` already calls `cookies()` on every route that touches the user's own data, so essentially every real screen (Phase 4 onward) was always going to be dynamic regardless — this only newly affects today's placeholder/dev-only routes (`/`, `/dev/tokens`, `/dev/components`), which aren't representative of the app's final shape. Worth knowing, not worth working around, for a single-user authenticated app with no public/SEO surface.
- **`useT()` takes the `{ en, ko }` pair inline at the call site** (`t({ en: "Dashboard", ko: "홈" })`) rather than a centrally pre-registered key path, per `docs/build-prompt.md` §9 ("타입 세이프한 사전 객체 + useT() 훅으로 충분히 구현한다") — no screen's real copy exists yet beyond what Phase 3 touches (the login screen, which has no mock either — both locales' copy there are original, chosen to read naturally per docs/README.md §9's own example of non-literal pairing), so there is nothing to key yet. A centralized dictionary can replace this later if duplicate pairs across call sites become a real problem; noting the option here rather than building it before it's needed.
- **Zod validation messages are locale-aware too, client-side only.** `schema.ts` exports `createLoginSchema(locale)`; the client (`LoginForm`) builds it from `useLocale()` so field errors read in the same language as the rest of the screen. The server action's defense-in-depth re-validation has no viewport to read, so it always uses the English default — that path only surfaces if JS is disabled or the request was malformed, not a real user-facing case.

**`settings.locale` — dropped.** A manual-override reinterpretation was proposed here (nullable, or a new `'auto'` value alongside `'ko'`/`'en'`) but rejected by the user: viewport decides language, full stop — no override means no column, and an unused setting left sitting in the schema just invites confusion later about why it's there. `20260909170000_drop_settings_locale.sql` drops it; `handle_new_user`'s `insert into public.settings (user_id) ...` needed no change (it only ever relied on column defaults). Applied to the live project and verified directly via `psql` — the column is gone, the existing settings row survived untouched on its other columns, and `database.types.ts` was regenerated to match.

## Phase 4a — New trade form

Four open questions were put to the user before building; all four confirmed, with two adjustments noted below.

**The mock's form is incomplete relative to its own data model.** Mock 1b has exactly 13 labelled fields (Instrument, Date, Session, HTF bias, HTF pairing, Range high, Range low, Entry, Stop, Target, Size, Entry model, Result) and **no Exit input** — yet `realizedR = (exit − entry) / risk`, so a trade logged from those fields alone produces no R at all, and every R on the dashboard, calendar, equity curve and Capital screen would be blank. Trade detail (2b) meanwhile displays Exit, Hold, Exit reason and "93% captured". README's own entity list and the build prompt's SQL both carry `exit`/`exit_reason`/`hold_minutes`. Applying `docs/build-prompt.md` §1 (README wins over the canvas), **Exit was added to the Execution section** as an optional field. Exit reason and hold minutes belong to Trade detail's edit path in 4c.

- **Required (blocks save) = exactly the NOT NULL columns the user must supply**: instrument, date, direction, session, htf pairing, range high, range low, entry, stop, size. README's own shorter list ("instrument, date, entry, stop") predates the schema; the extra four are all columns the database refuses to accept as null.
- **An open trade saves.** Exit and result are both optional and independent. A trade with no exit is simply still running: `realizedR` is null, so Phase 2's selectors skip it for net R and expectancy while it still counts toward win rate if a result was set. That asymmetry is deliberate and was confirmed in Phase 2.
- **`result` is auto-suggested from the exit's sign, then locked.** Once the trader picks a result by hand, a `resultTouched` flag stops the suggestion from ever overwriting it again — including on later exit edits. **Adjustment requested by the user**, and the reason is sound: the app must never silently overrule a judgement the trader has already made.
- **Blocking stops where the database stops**: stop ≠ entry, range high > low, size > 0, and unparseable numbers. Everything softer is a warning rendered under the form that never disables the save — target on the same side of entry as the stop, entry outside the range, off-plan, a retired model, a result that disagrees with the exit, and drawdown within 2 points of the limit. **A future-set date was dropped from the warning list at the user's request**: it's a rare slip, and a form that cries wolf gets all its warnings ignored.
- **Sweep side is derived from the stop, with an override.** `deriveSweepSide`: stop below the range low → low purged, above the high → high purged, inside → no sweep. README says it's "inferred from which extreme was purged" but never from what; the Playbook's own C2 rule 4 ("Stop beyond the sweep wick") does. Verified against the mock's own numbers — stop 23,396.50 against a 23,402.75 low derives "low", exactly the "Low purged" the mock prints. `both` is unreachable by inference, so the panel offers an explicit override.
- **`size` stays required and is record-keeping only.** It feeds no calculation (`pnlAmount` is `realizedR × rValueAtEntry`), but the column is already NOT NULL, a journal entry without position size is half a record, and it's known the moment the order is placed. Labelled in lots, since the confirmed instrument set is 28 FX pairs plus XAUUSD.
- **`rValueAtEntry` is computed, read-only, and recomputed server-side on submit.** The form shows "1R today · $X — frozen onto this trade when you log it"; the value the row actually stores is recalculated in the server action from the account and its ledger, never taken from the client. Hand-editing it is deliberately impossible: it would break the invariant the whole Capital screen rests on and silently desync money from R. (Phase 6's CSV import will need a per-row value, since historical trades' 1R can't be derived from today's balance — flagged for then.)
- **No account → a first-run setup sheet, not a guessed default.** `accounts` was genuinely empty, and `trades.account_id`/`r_value_at_entry` are both NOT NULL, so this is the real first-run path rather than an edge case. Auto-creating an account with an invented starting capital was rejected outright — that number drives every figure on the Capital screen. The sheet asks only what a trade needs (name, starting capital, risk %, drawdown limit), previews the resulting 1R, and Phase 8's Capital screen will edit this same row rather than create a competing one. Closing it returns to the dashboard.
- **Models select stays optional** with a "No models yet — add them in Playbook" empty state; trades without a model group under "Unassigned", which Phase 2's `byModel` already handles.

Verified end to end against the mock's own trade in a real browser: range size 83.50, sweep side "Low purged", 50% level 23,444.50, R:R "1 : 5.2R" and realized "+2.8R" all match mock 1b/2b exactly. Then checked the two paths that matter most — a closed trade stored `r_value_at_entry` 150 (15,000 × 1%), and a second, open trade stored exit and result as NULL with `r_value_at_entry` 154.22, correctly recomputed from the balance the first trade had moved. Test account and user deleted afterwards.

**Two bugs in the Phase 3 `Modal` primitive that only real interaction exposed**, both invisible to build/lint/tsc and to the Phase 3 gallery check:

- **Focus theft ate keystrokes.** `Modal`'s setup effect listed `onClose` in its dependencies, and every caller passes an inline arrow, so the effect re-ran on every parent render and called `panelRef.current.focus()` — pulling focus out of whatever field was being typed into. Only the first character of any input inside a modal survived. Fixed by holding `onClose` in a ref so the effect depends on `open` alone.
- **The portal broke hydration.** `Modal` guarded its portal with `typeof document === "undefined"`, so the server rendered nothing while the client rendered the portal on its very first pass — a mismatch that made React discard and rebuild the subtree, wiping typed-in state with it. Fixed with a `mounted` flag so both first renders agree on null. The gallery never caught this because its modal only opens after hydration; the account gate renders open on first paint, which exposed it immediately.
