# Decisions

One line per decision made where the spec was silent, ambiguous, or (rarely) contradicted itself. Newest at the bottom, grouped by phase.

## Phase 0

- **Repo location.** The session's shell started in `/Users/seungmin` (the whole home directory, already an empty untracked git repo — not something to build into) and later in `/Users/seungmin/Documents/trading-journal`, an existing, unrelated trading-journal app (Prisma/Express/Docker) that `docs/build-prompt.md` §0 explicitly says not to reference or reuse. Created a fresh repo at `/Users/seungmin/Documents/min-journal` instead. **Confirmed correct by the user.**
- **Home-directory git repo removed.** `/Users/seungmin/.git` (zero commits, plain `git init` output, predates this session) was deleted at the user's request — a repo rooted at the whole home directory was flagged as a future hazard regardless of who created it.
- **`docs/` folder name.** The handed-off bundle's docs folder was named `docs:` (a colon, not a slash) on disk — an extraction artifact, not a spec choice. Copied its contents into `docs/` (no colon) in the new repo.
- **Storage architecture — README vs. build prompt.** `docs/README.md` (Overview, and "State Management" → Storage) recommends a local-first SPA persisting to IndexedDB, explicitly out of scope for sync in v1. `docs/build-prompt.md` §2 locks in Next.js 15 + Supabase (Postgres + Auth + Storage). **Confirmed by the user: Next.js + Supabase, final.** Reason given — the phone needs direct access, and chart screenshots must be shared between PC and mobile (a local-only store on one device can't do either). The README's local-first paragraph is superseded and ignored; everything else in README (screens, copy, tokens, entity shapes) still governs.
- **Next.js version.** `create-next-app@latest` scaffolds Next 16 today; pinned `next` and `eslint-config-next` to `15.5.25` (latest stable 15.x) to match the locked spec.
- **ESLint flat-config bridge.** `eslint-config-next@15.x` still ships the legacy eslintrc format (its native flat-config export ships in v16), so `eslint.config.mjs` bridges it with `@eslint/eslintrc`'s `FlatCompat`, loaded via `createRequire` (Next's internal lint step doesn't reliably follow the package's ESM `exports` condition). Routine compatibility plumbing, not a design decision — noted here in case it looks surprising in review.
- **Pretendard delivery.** Self-hosted the **variable** font file (`pretendard/dist/web/variable/pretendardvariable.css`, ~2MB, one file covering the full weight axis) rather than four separate static weight files (~3MB combined for 500/600/700/800). Same visual result, smaller download.
- **Western P&L convention colors.** `docs/README.md` deliberately leaves these unspecified ("expose the convention as a setting... rather than hardcoding" — no hex given). Chose gain `#22c55e` / loss `#f04452` (reusing the existing KR-gain red for the western loss role, since western loss=red is the same hue already in the palette). Both pairs live behind CSS variables (`--pnl-gain` / `--pnl-loss`, swapped by `[data-pnl="west"]` on `<html>`), so this is a one-line change if the user has a different pair in mind.
- **Tailwind theme keys for half-step sizes.** CSS custom-property names can't contain a bare `.`, so the type scale's half-steps (11.5, 12.5, …) are keyed as `--text-11_5` etc., producing utility classes like `text-11_5`. Verified these actually emit CSS (not just silently dropped) via the production build output.

## Phase 1 — additional decisions

- **`settings` row provisioning.** Nothing in the spec says how a user's `settings` row comes to exist (there's no sign-up flow to attach it to). A Postgres trigger on `auth.users` insert (`handle_new_user`) seeds one default `settings` row (`locale='ko'`, `pnl_convention='kr'`, `default_instrument='EURUSD'`, `default_session='asia'`, `r_precision=1`). `accounts` are **not** auto-seeded the same way — starting capital, currency, and risk mode need real user input, so the first account is created through onboarding UI (Phase 8), not a trigger default.
- **`session` default.** README doesn't state one; picked `asia` (the first session of the trading day) as `default_session`'s seed value. Easy to change in Settings once that screen exists.
- **`r_precision` default.** Not specified; seeded at `1` (one decimal place on R values, matching every R value shown in the mocks, e.g. "+18.4R").
- **Storage bucket RLS.** `chart-shots` is private; objects are scoped by putting the owning user's id as the first path segment (`{user_id}/{trade_id}/{filename}`) and writing storage RLS policies against `auth.uid()::text = (storage.foldername(name))[1]` — the standard Supabase per-user-folder pattern, since `storage.objects` has no `user_id` column of its own to key RLS on directly.
- **`CHECK` constraints, not native Postgres enums, for `direction` / `session` / `htf_pairing` / `result` / etc.** Keeps future value changes a plain migration (`ALTER TABLE ... DROP/ADD CONSTRAINT`) instead of `ALTER TYPE` ceremony (which can't drop values). Trade-off: `supabase gen types` can only narrow to a literal union from a real Postgres enum, so these columns come back as plain `string` in `database.types.ts`. Tighter literal-union types + zod schemas for these fields belong in `src/lib/domain/` once that lands in Phase 2 — the generated file is intentionally the loose, raw-schema layer, not the app-facing one.
- **Migrations validated locally before handoff.** Ran `pnpm exec supabase start` (local Docker Postgres + auth + storage) once, applied all four migrations against it end to end with no errors, generated `src/lib/database.types.ts` from that local instance, then `supabase stop`.
- **Login screen has no mockup** (`docs/README.md` § Routes lists `/login` with none). Built plain with tokens directly rather than Button/Input primitives, since Phase 3 (design system) hasn't landed yet — functionally complete now, worth a pass to swap in the shared primitives once Phase 3 exists.
- **Bug found + fixed: `loginSchema` couldn't be exported from `actions.ts`.** That file is `"use server"`, which only supports async-function exports (server actions) — re-exporting the zod schema object from it corrupted the object across the server/client bundle boundary, and `zodResolver` threw `Invalid input: not a Zod schema` at runtime. Moved `loginSchema`/`LoginInput` into `src/app/login/schema.ts` (no `"use server"`), imported by both `actions.ts` and `login-form.tsx`. Caught by actually loading `/login` in a browser, not by `pnpm build` (Next's prerendering never executes the client component's `zodResolver()` call, so the build stayed green through this).

## Phase 1 — bug found by opening `/login` in a real browser: Tailwind spacing was 4x too large everywhere

The user reported `/login` rendering broken — tall narrow card, square inputs, a button that didn't stretch, system font instead of Pretendard. `pnpm build`/`lint`/`test` were all green throughout; none of them would have caught this.

- **Root cause:** Tailwind's default `--spacing` base unit is `0.25rem` (4px) — bare numeric spacing utilities (`p-32`, `gap-16`, `w-32`, `px-16`, ...) compute to `N * 4px`, not `N px`. Every spacing value in `docs/README.md`'s Design Tokens is already a literal px number, and every component written so far (`/login`, `/dev/tokens`, `/`) used those numbers directly as Tailwind class suffixes (e.g. `p-32` meaning "32px"), assuming a 1:1 mapping that Tailwind does not use. Confirmed in a real browser via computed styles: `p-32` on the login card computed to `padding: 128px`, not `32px` — 4x over, exactly matching the multiplier.
- **Why colors/radius/font-size looked fine:** those come from custom `@theme` keys with fixed, explicit px values (`--radius-24: 24px`, `--text-56: 56px`, ...), not from Tailwind's dynamic spacing-multiplier scale — only the spacing-derived utilities (padding/margin/gap/width/height/inset) were affected.
- **The font was not actually broken** — `document.fonts` showed `"Pretendard Variable"` loaded and applied on every element checked. The 4x spacing bug made the layout collapse enough that Pretendard's fairly plain Latin letterforms read as a generic system font at a glance; there was no separate font-loading bug to fix.
- **Fix:** redefined `--spacing: 1px` inside the `@theme` block in `globals.css`, rather than rewriting every call site to the `N/4` form (verified first that the codebase has zero existing usages of Tailwind's fractional spacing convention like `p-1.5`/`gap-2.5`, so there was nothing to conflict with). One-line change, fixes every page at once.
- **Verified the fix in a real browser, not just a rebuild:** re-inspected computed styles on `/login` (card padding now `32px`, email input width now `316px` = 380 − 2×32, button padding `17px`), then logged into `/dev/tokens` and `/` with a second disposable test user (created and deleted the same way as the Phase 1 login test) and visually confirmed every section — colors, type scale, radius swatches, spacing bars — renders correctly, not just the one page that was reported broken.
- Fixed a stale, now-wrong claim in `/dev/tokens`'s own copy ("Tailwind default scale — 4px base already matches") to describe the actual `--spacing: 1px` override instead.

## Phase 2 — domain logic

Four rules the spec left open, put to the user and confirmed before implementing:

- **Break-even R.** `result` is a label, never an input to the R maths: `realizedR` always comes from the actual exit, so a 'be' trade lands at ~0.0R on its own instead of being forced to exactly 0. Keeps `pnlAmount` (and therefore the balance series) reconcilable with the real account when a "break even" exit was a few ticks off. **No exit → `realizedR` is `null`, not 0**, and such trades are skipped by the aggregates rather than counted as zeros (counting them would quietly drag net R and expectancy toward zero).
- **Break-even in the aggregates.** Win rate = wins / trades-with-a-result, so BE sits in the denominator only — mock 2c prints "67%" with the sub-line "6 / 9", i.e. the denominator is the trade count. Avg win / avg loss exclude BE entirely. Expectancy includes it (a scratch really does dilute expectancy). **Win streaks treat BE as neutral** — it neither extends nor breaks a run, it is skipped; only a loss resets. A trade with no result yet is skipped the same way.
- **Mid-range band = `MID_RANGE_HALF_BAND` (0.10), i.e. 40%–60%.** Symmetric around the 50% equilibrium line, the only range level `docs/README.md` actually draws. Sanity check: the one trade the canvas chips "On plan" (mock 2b) has its entry at 9.9% of the range, far outside the band. Kept as a named constant so it can move into Settings later.
- **`offPlan` is trade-local: `sweepSide === 'none' || entryIsMidRange`.** Model retirement is deliberately *not* an input. `offPlan` is recomputed on every read, so including model status would retroactively flip already-logged trades to off-plan the moment a model is retired — silently rewriting history and moving past adherence numbers, which a trading journal must never do. README §Playbook ("retiring ... marks future matches off-plan") and the retired model's mock description ("new entries are flagged off-plan") are therefore read as applying **only to trades recorded after the retirement**, honoured as a warning in the trade form at log time. The mock stays consistent either way: its 8 off-plan trades all belong to the retired "Mid-range entry" model, whose own description is "No sweep, no confirmation" — so they are already off-plan via `sweepSide === 'none'`.
- **Rule adherence = (trades − off-plan trades) / trades**, over every trade in the period (BE included), reading the derived `offPlan` flag — *not* the manual "On plan" tag, which is a separate self-assessment tag sharing a row with Impatient / Chased entry / Early exit. Not a judgement call: reverse-engineered from two independent mocks and confirmed. Weekly 2c shows 89% with "1 off-plan" over a 9-trade week ((9−1)/9 = 88.9%); dashboard 1a shows 87% over 61 trades (24+18+11+8, matching "View all 61") of which the 8 "Mid-range entry" ones are flagged ((61−8)/61 = 86.9%). Both are locked in as regression tests.
- **Time-weighted return is chain-linked.** The timeline is cut into sub-periods at every cash movement; each sub-period returns (trading P&L / balance at the start of that sub-period); the factors are multiplied. Sub-periods starting at a balance ≤ 0 are skipped rather than dividing by zero; no trades at all → 0%. **Mock 3a's "Return on capital +43.0%" is not a TWR** — it is the same number as the "+43.0R lifetime" printed beside it, i.e. the plain sum of R at 1% risk, and was judged to be the mock author reusing the R figure rather than specifying the maths. We compute the real thing, which is what README's own "time-weighted, so deposits don't inflate it" asks for. Covered by a test where TWR is 21% while the naive money-weighted view would read 15.5%.

Smaller calls made while implementing, none of them spec'd:

- **Same-date event ordering: cash movements before trades**, `createdAt` as the final tiebreak — a deposit dated D funds that day's trading. Makes the balance series, the TWR sub-periods, and the ledger's running-balance column all deterministic.
- **"Win streak" is ambiguous in the mock** (dashboard shows "4 trades" with no sub-line, so it could be the current run or the best one). `winStreaks` returns **both** `longest` and `current` rather than guessing; the dashboard will use `longest`. Cheap, and it removes the guess.
- **Selectors return raw ratios (0..1), never pre-rounded percentages.** Display rounding (adherence to a whole %, R to `settings.r_precision`) belongs to the UI, so one selector can feed both a stat card and a chart. Tests assert both the raw value and the rounded one the mock shows.
- **Domain types are camelCase and carry real literal unions**, bridging the loose generated `database.types.ts` (where CHECK-constrained columns are plain `string`). The row → domain mapper lands with the queries in Phase 4.
- **Dates are compared as `YYYY-MM-DD` strings**, never `Date` objects — lexicographic order is chronological order and there is no timezone to get wrong.
- **Currency is left at full float precision in the domain**; rounding is display-only. Tests compare money to the cent (`toBeCloseTo(x, 2)`) since e.g. 9.68R × $1,000 lands on 9680.000000000002.
- **Drawdown warning margin is 2 *percentage points*** (`DRAWDOWN_WARNING_MARGIN_PCT`), so a 10% limit starts warning at 8% drawdown — the natural reading of README's "within 2% of the limit". Cross-checked against the mock: peak $32,180 with a −10% limit gives "Stop trading at −$3,218".
- **Mock 2b's "93% captured" is a rounding artifact**, like the 43.0% above: 2.8103R / 3.0R is 93.7%. Both displayed numbers in the mock are themselves rounded, so there is no real conflict — `captureRate` computes from raw values.
