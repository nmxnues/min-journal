## Phase 1 — additional decisions

- **`settings` row provisioning.** Nothing in the spec says how a user's `settings` row comes to exist (there's no sign-up flow to attach it to). A Postgres trigger on `auth.users` insert (`handle_new_user`) seeds one default `settings` row (`pnl_convention='kr'`, `default_instrument='EURUSD'`, `default_session='asia'`, `r_precision=1` — `locale` was part of this row too until it was dropped, see the Phase 3 follow-up entry below). `accounts` are **not** auto-seeded the same way — starting capital, currency, and risk mode need real user input, so the first account is created through onboarding UI (Phase 8), not a trigger default.
- **`session` default.** README doesn't state one; picked `asia` (the first session of the trading day) as `default_session`'s seed value. Easy to change in Settings once that screen exists.
- **`r_precision` default.** Not specified; seeded at `1` (one decimal place on R values, matching every R value shown in the mocks, e.g. "+18.4R").
- **Storage bucket RLS.** `chart-shots` is private; objects are scoped by putting the owning user's id as the first path segment (`{user_id}/{trade_id}/{filename}`) and writing storage RLS policies against `auth.uid()::text = (storage.foldername(name))[1]` — the standard Supabase per-user-folder pattern, since `storage.objects` has no `user_id` column of its own to key RLS on directly.
- **`CHECK` constraints, not native Postgres enums, for `direction` / `session` / `htf_pairing` / `result` / etc.** Keeps future value changes a plain migration (`ALTER TABLE ... DROP/ADD CONSTRAINT`) instead of `ALTER TYPE` ceremony (which can't drop values). Trade-off: `supabase gen types` can only narrow to a literal union from a real Postgres enum, so these columns come back as plain `string` in `database.types.ts`. Tighter literal-union types + zod schemas for these fields belong in `src/lib/domain/` once that lands in Phase 2 — the generated file is intentionally the loose, raw-schema layer, not the app-facing one.
- **Migrations validated locally before handoff.** Ran `pnpm exec supabase start` (local Docker Postgres + auth + storage) once, applied all four migrations against it end to end with no errors, generated `src/lib/database.types.ts` from that local instance, then `supabase stop`.
- **Login screen has no mockup** (`docs/README.md` § Routes lists `/login` with none). Built plain with tokens directly rather than Button/Input primitives, since Phase 3 (design system) hadn't landed yet. **Refactored onto `Field`/`Input`/`Button` at the end of Phase 3**, as flagged here.
- **Bug found + fixed: `loginSchema` couldn't be exported from `actions.ts`.** That file is `"use server"`, which only supports async-function exports (server actions) — re-exporting the zod schema object from it corrupted the object across the server/client bundle boundary, and `zodResolver` threw `Invalid input: not a Zod schema` at runtime. Moved `loginSchema`/`LoginInput` into `src/app/login/schema.ts` (no `"use server"`), imported by both `actions.ts` and `login-form.tsx`. Caught by actually loading `/login` in a browser, not by `pnpm build` (Next's prerendering never executes the client component's `zodResolver()` call, so the build stayed green through this).

## Phase 1 — bug found by opening `/login` in a real browser: Tailwind spacing was 4x too large everywhere

The user reported `/login` rendering broken — tall narrow card, square inputs, a button that didn't stretch, system font instead of Pretendard. `pnpm build`/`lint`/`test` were all green throughout; none of them would have caught this.

- **Root cause:** Tailwind's default `--spacing` base unit is `0.25rem` (4px) — bare numeric spacing utilities (`p-32`, `gap-16`, `w-32`, `px-16`, ...) compute to `N * 4px`, not `N px`. Every spacing value in `docs/README.md`'s Design Tokens is already a literal px number, and every component written so far (`/login`, `/dev/tokens`, `/`) used those numbers directly as Tailwind class suffixes (e.g. `p-32` meaning "32px"), assuming a 1:1 mapping that Tailwind does not use. Confirmed in a real browser via computed styles: `p-32` on the login card computed to `padding: 128px`, not `32px` — 4x over, exactly matching the multiplier.
- **Why colors/radius/font-size looked fine:** those come from custom `@theme` keys with fixed, explicit px values (`--radius-24: 24px`, `--text-56: 56px`, ...), not from Tailwind's dynamic spacing-multiplier scale — only the spacing-derived utilities (padding/margin/gap/width/height/inset) were affected.
- **The font was not actually broken** — `document.fonts` showed `"Pretendard Variable"` loaded and applied on every element checked. The 4x spacing bug made the layout collapse enough that Pretendard's fairly plain Latin letterforms read as a generic system font at a glance; there was no separate font-loading bug to fix.
- **Fix:** redefined `--spacing: 1px` inside the `@theme` block in `globals.css`, rather than rewriting every call site to the `N/4` form (verified first that the codebase has zero existing usages of Tailwind's fractional spacing convention like `p-1.5`/`gap-2.5`, so there was nothing to conflict with). One-line change, fixes every page at once.
- **Verified the fix in a real browser, not just a rebuild:** re-inspected computed styles on `/login` (card padding now `32px`, email input width now `316px` = 380 − 2×32, button padding `17px`), then logged into `/dev/tokens` and `/` with a second disposable test user (created and deleted the same way as the Phase 1 login test) and visually confirmed every section — colors, type scale, radius swatches, spacing bars — renders correctly, not just the one page that was reported broken.
- Fixed a stale, now-wrong claim in `/dev/tokens`'s own copy ("Tailwind default scale — 4px base already matches") to describe the actual `--spacing: 1px` override instead.

## Phase 2 — domain logic

Four rules the spec left open, put to the user and confirmed before implementing:

- **Break-even R.** `result` is a label, never an input to the R maths: `realizedR` always comes from the actual exit, so a 'be' trade lands at ~0.0R on its own instead of being forced to exactly 0. Keeps `pnlAmount` (and therefore the balance series) reconcilable with the real account when a "break even" exit was a few ticks off. **No exit → `realizedR` is `null`, not 0**, and such trades are skipped by the aggregates rather than counted as zeros (counting them would quietly drag net R and expectancy toward zero).
- **Break-even in the aggregates.** Win rate = wins / trades-with-a-result, so BE sits in the denominator only — mock 2c prints "67%" with the sub-line "6 / 9", i.e. the denominator is the trade count. Avg win / avg loss exclude BE entirely. Expectancy includes it (a scratch really does dilute expectancy). **Win streaks treat BE as neutral** — it neither extends nor breaks a run, it is skipped; only a loss resets. A trade with no result yet is skipped the same way.
- **Mid-range band = `MID_RANGE_HALF_BAND` (0.10), i.e. 40%–60%.** Symmetric around the 50% equilibrium line, the only range level `docs/README.md` actually draws. Sanity check: the one trade the canvas chips "On plan" (mock 2b) has its entry at 9.9% of the range, far outside the band. Kept as a named constant so it can move into Settings later.
- **`offPlan` is trade-local: `sweepSide === 'none' || entryIsMidRange`.** Model retirement is deliberately *not* an input. `offPlan` is recomputed on every read, so including model status would retroactively flip already-logged trades to off-plan the moment a model is retired — silently rewriting history and moving past adherence numbers, which a trading journal must never do. README §Playbook ("retiring ... marks future matches off-plan") and the retired model's mock description ("new entries are flagged off-plan") are therefore read as applying **only to trades recorded after the retirement**, honoured as a warning in the trade form at log time. The mock stays consistent either way: its 8 off-plan trades all belong to the retired "Mid-range entry" model, whose own description is "No sweep, no confirmation" — so they are already off-plan via `sweepSide === 'none'`.
- **Rule adherence = (trades − off-plan trades) / trades**, over every trade in the period (BE included), reading the derived `offPlan` flag — *not* the manual "On plan" tag, which is a separate self-assessment tag sharing a row with Impatient / Chased entry / Early exit. Not a judgement call: reverse-engineered from two independent mocks and confirmed. Weekly 2c shows 89% with "1 off-plan" over a 9-trade week ((9−1)/9 = 88.9%); dashboard 1a shows 87% over 61 trades (24+18+11+8, matching "View all 61") of which the 8 "Mid-range entry" ones are flagged ((61−8)/61 = 86.9%). Both are locked in as regression tests.
- **Time-weighted return is chain-linked.** The timeline is cut into sub-periods at every cash movement; each sub-period returns (trading P&L / balance at the start of that sub-period); the factors are multiplied. Sub-periods starting at a balance ≤ 0 are skipped rather than dividing by zero; no trades at all → 0%. **Mock 3a's "Return on capital +43.0%" is not a TWR** — it is the same number as the "+43.0R lifetime" printed beside it, i.e. the plain sum of R at 1% risk, and was judged to be the mock author reusing the R figure rather than specifying the maths. We compute the real thing, which is what README's own "time-weighted, so deposits don't inflate it" asks for. Covered by a test where TWR is 21% while the naive money-weighted view would read 15.5%.

Smaller calls made while implementing, none of them spec'd:

- **Same-date event ordering: cash movements before trades**, `createdAt` as the final tiebreak — a deposit dated D funds that day's trading. Makes the balance series, the TWR sub-periods, and the ledger's running-balance column all deterministic.
- **"Win streak" is ambiguous in the mock** (dashboard shows "4 trades" with no sub-line, so it could be the current run or the best one). `winStreaks` returns **both** `longest` and `current` rather than guessing. **The dashboard shows `current`** — decided by the user: a streak is a read on the state you are in right now, not a personal-best record. `longest` stays on the selector (it costs nothing and the weekly review may want it) but is not on any screen.
- **Selectors return raw ratios (0..1), never pre-rounded percentages.** Display rounding (adherence to a whole %, R to `settings.r_precision`) belongs to the UI, so one selector can feed both a stat card and a chart. Tests assert both the raw value and the rounded one the mock shows.
- **Domain types are camelCase and carry real literal unions**, bridging the loose generated `database.types.ts` (where CHECK-constrained columns are plain `string`). The row → domain mapper lands with the queries in Phase 4.
- **Dates are compared as `YYYY-MM-DD` strings**, never `Date` objects — lexicographic order is chronological order and there is no timezone to get wrong.
- **Currency is left at full float precision in the domain**; rounding is display-only. Tests compare money to the cent (`toBeCloseTo(x, 2)`) since e.g. 9.68R × $1,000 lands on 9680.000000000002.
- **Drawdown warning margin is 2 *percentage points*** (`DRAWDOWN_WARNING_MARGIN_PCT`), so a 10% limit starts warning at 8% drawdown — the natural reading of README's "within 2% of the limit". Cross-checked against the mock: peak $32,180 with a −10% limit gives "Stop trading at −$3,218".
- **Mock 2b's "93% captured" is a rounding artifact**, like the 43.0% above: 2.8103R / 3.0R is 93.7%. Both displayed numbers in the mock are themselves rounded, so there is no real conflict — `captureRate` computes from raw values.

## Phase 3 — design system primitives

- **`clsx` + `tailwind-merge` added.** Not a component kit (the build prompt bars those) — they are the class-merging utility that lets a caller's `className` actually override a component default, which plain string concatenation cannot do (CSS source order decides, not string order).
- **tailwind-merge had to be taught this project's scales, and silently corrupted components until it was.** Our type scale is keyed by px number (`text-13`, `text-11_5`), which collides with Tailwind's text-*colour* namespace: out of the box tailwind-merge classified `text-13` as a colour and dropped the earlier `text-white`, so the `ink` button rendered as **black text on a black fill**. The px-named radius scale had the same problem in reverse (`rounded-24` and `rounded-8` never deduped). `src/lib/cn.ts` now extends the merge config with both scales. Caught by looking at `/dev/components` in a browser — `pnpm build`, `lint`, and `tsc` were all green with the bug in place, which is the same shape of failure as the Phase 1 zodResolver bug and the Phase 2 spacing bug.
- **The capital chart's 1R line gets its own vertical band** (viewBox y 62%–89%, matching the mock's 106–152 of 170) rather than being stretched over the full height. 1R is a fixed percentage of the balance, so on a full-height "own scale" it normalises to the *exact same shape* as the balance line and disappears underneath it — which is precisely what happened on first render. Confirmed against the mock rendered in a browser, where the 1R line clearly sits lower and flatter than the balance line.
- **`BottomTabBar` is designed, not mocked.** The 1d mobile mock has no tab bar (its home screen ends at the "기록하기" CTA), but the build prompt requires one for mobile nav. Built from the TopBar's vocabulary — active takes ink, inactive stays muted — with every target over the 44px minimum and `env(safe-area-inset-bottom)` padding.
- **`RangeDiagram` is built with divs, in Phase 3**, per the build prompt's note that it is layout rather than a chart. Vertical position is price (top edge = range high, bottom = range low, hairline = 50% equilibrium); horizontal offsets are reading order only and match the mock's. The "Sweep" label landing on the same line as the caption row was checked against the canvas rendered in a browser — the mock does the same thing, so it is faithful rather than a bug.
- **`EmptyState` is designed, not mocked**, as docs/README.md § Empty states asks: the card vocabulary at rest, a 700 16px title over a 500 13.5px line, with one optional action.
- **Charts reproduce the mocks' `preserveAspectRatio="none"`**, so strokes stretch horizontally with the container exactly as the mock does. That is deliberate fidelity, not an oversight.

### 2. Letter-spacing / line-height / gaps reading wider than the mock

Three real, verified discrepancies, all against a spec that turned out to have more variants than the primitives modeled:

- **StatCard had an invented 28px size that doesn't exist in README's own type scale.** The canvas mock does use 28px in one place (Capital's 4-up row), but `docs/README.md`'s Design Tokens § Typography lists the scale explicitly and 28 is not in it (11/11.5/12/.../26/30/44/56). Also found: **the calendar summary row's 26px values carry no letter-spacing at all** in the canvas markup, while every 28px+ value explicitly sets `-0.03em` — an intentional-looking distinction, not an oversight, so `StatCard` now has exactly two variants (`sm`: 26px, no tracking; `lg`: 30px, `-.03em`) instead of one shared tracking class.
- **`BarRow`'s caption line used `margin-top:8px`; the mock uses 6px.** The bar's own margin-top does equal its track height (8px for an 8px track, 7px for a 7px track — that part was already right), but the caption below it is a separate, smaller gap. ### 5. Language is decided by viewport width, not `settings.locale`

Confirmed rule: **≥900px → English** (matches the responsive breakpoint already used for layout — docs/README.md's own `<900px` language), reading the PC mocks (1a-1c, 2a-2d, 3a); **<900px → Korean**, reading the 1d / 3b-mobile mocks. Reasoning given: mobile is for logging a trade in the moment (native language reads faster under time pressure), desktop is for analysis (trading terms read more naturally in English, which is also what every PC mock is authored in). Not a user setting — the same one responsive codebase now branches copy the same way it already branches layout, with no `/mobile` route.

**Mechanism — `src/lib/i18n/` (`locale.ts` + `locale-context.tsx`):**

- `getViewportLocale(width)` is the single source of truth for the breakpoint (900px, `LOCALE_BREAKPOINT_PX`, deliberately identical to the layout breakpoint already in the responsive rules — one number, not two that could drift apart).
- **No-flicker strategy, and why it doesn't need a blocking `<head>` script:** the classic "avoid flash" pattern (à la `next-themes` for dark mode) uses a blocking inline script to mutate the DOM before React ever mounts, because that trick is for a CSS class toggle — trivial vanilla-JS DOM work with nothing to reconcile. This is different: the payload is *text content*, which has to go through React's tree regardless (there is no CSS-only way to swap arbitrary Korean/English strings without rendering both languages into the DOM at once, which does not scale as the app's i18n mechanism for every future screen's copy — see the tradeoff note below). So instead:
  1. **`RootLayout` (Server Component) reads the `viewport-locale` cookie** (`cookies()`, Next 15's async API) and renders `<html lang>` and the `LocaleProvider`'s starting state from it. Once a visitor has been here before, this is correct from the very first byte the server sends — no client correction ever runs.
  2. The **only** time the guess can be wrong is a visitor's first-ever request, when no cookie exists yet — the server then defaults to `"en"`. `LocaleProvider` initializes its React state to that exact server-provided value (required: the client's first render must match the server's or React throws a hydration-mismatch error), then in a **`useLayoutEffect`** — which fires synchronously after the DOM commits but strictly *before the browser paints* — measures the real `window.innerWidth` and corrects the state if it disagrees, and writes the cookie for every future visit. Because this runs before paint, the correction is invisible; there is nothing to see flash.
  3. That same effect attaches a `matchMedia('(min-width: 900px)')` listener, so live resizing across the breakpoint (a desktop window resize, a tablet rotation) updates the locale immediately with no reload.
  - **Verified live in a browser**, not just read from the code: resized an actual window from 1400px to 700px and back. At 700px, `document.cookie` showed `viewport-locale=ko`, `document.documentElement.lang` was `"ko"`, and both `TopBar`'s and `BottomTabBar`'s nav labels (pulled from the *same* shared dictionary via `t()`) switched to Korean live, with no reload; resizing back to 1400px flipped both back to English live. (This sandbox's browser window doesn't let its CSS viewport track `resize_window` reliably — the first couple of attempts read back the old width — so this was confirmed by re-reading `window.innerWidth` after the resize each time until it actually reflected the new size, not by trusting the resize call alone.)
- **A real bug this caught that `pnpm build`/`lint`/`tsc` all missed**, the same shape as the Phase 1 `zodResolver` bug and the Phase 3 `tailwind-merge` bug: `parseInitialLocale` was originally defined in `locale-context.tsx`, which is a `"use client"` module. Next's RSC compiler does not allow a Server Component to call a plain function imported from a `"use client"` file directly (only render it as a Component, or pass it down as a prop) — `RootLayout` calling it threw `Attempted to call parseInitialLocale() from the server` at request time, a 500 on every single route, invisible to any static check because the type signatures are fine and nothing about it is wrong until it actually executes on a real request. Fixed by moving the function into `locale.ts` (no `"use client"`), which is safely importable from both sides.
- **Side effect: every route is now dynamically rendered** (`ƒ` instead of `○` in the build output), because `RootLayout` calling `cookies()` opts the whole tree out of static generation. Judged a non-issue here: `src/lib/supabase/server.ts`'s `createClient()` already calls `cookies()` on every route that touches the user's own data, so essentially every real screen (Phase 4 onward) was always going to be dynamic regardless — this only newly affects today's placeholder/dev-only routes (`/`, `/dev/tokens`, `/dev/components`), which aren't representative of the app's final shape. Worth knowing, not worth working around, for a single-user authenticated app with no public/SEO surface.
- **`useT()` takes the `{ en, ko }` pair inline at the call site** (`t({ en: "Dashboard", ko: "홈" })`) rather than a centrally pre-registered key path, per `docs/build-prompt.md` §9 ("타입 세이프한 사전 객체 + useT() 훅으로 충분히 구현한다") — no screen's real copy exists yet beyond what Phase 3 touches (the login screen, which has no mock either — both locales' copy there are original, chosen to read naturally per docs/README.md §9's own example of non-literal pairing), so there is nothing to key yet. A centralized dictionary can replace this later if duplicate pairs across call sites become a real problem; noting the option here rather than building it before it's needed.
- **Zod validation messages are locale-aware too, client-side only.** `schema.ts` exports `createLoginSchema(locale)`; the client (`LoginForm`) builds it from `useLocale()` so field errors read in the same language as the rest of the screen. The server action's defense-in-depth re-validation has no viewport to read, so it always uses the English default — that path only surfaces if JS is disabled or the request was malformed, not a real user-facing case.

**`settings.locale` — dropped.** A manual-override reinterpretation was proposed here (nullable, or a new `'auto'` value alongside `'ko'`/`'en'`) but rejected by the user: viewport decides language, full stop — no override means no column, and an unused setting left sitting in the schema just invites confusion later about why it's there. `20260909170000_drop_settings_locale.sql` drops it; `handle_new_user`'s `insert into public.settings (user_id) ...` needed no change (it only ever relied on column defaults). Applied to the live project and verified directly via `psql` — the column is gone, the existing settings row survived untouched on its other columns, and `database.types.ts` was regenerated to match.

## Phase 4a — New trade form

Four open questions were put to the user before building; all four confirmed, with two adjustments noted below.

**The mock's form is incomplete relative to its own data model.** Mock 1b has exactly 13 labelled fields (Instrument, Date, Session, HTF bias, HTF pairing, Range high, Range low, Entry, Stop, Target, Size, Entry model, Result) and **no Exit input** — yet `realizedR = (exit − entry) / risk`, so a trade logged from those fields alone produces no R at all, and every R on the dashboard, calendar, equity curve and Capital screen would be blank. Trade detail (2b) meanwhile displays Exit, Hold, Exit reason and "93% captured". README's own entity list and the build prompt's SQL both carry `exit`/`exit_reason`/`hold_minutes`. Applying `docs/build-prompt.md` §1 (README wins over the canvas), **Exit was added to the Execution section** as an optional field. Exit reason and hold minutes belong to Trade detail's edit path in 4c.

- **Required (blocks save) = exactly the NOT NULL columns the user must supply**: instrument, date, direction, session, htf pairing, range high, range low, entry, stop, size. README's own shorter list ("instrument, date, entry, stop") predates the schema; the extra four are all columns the database refuses to accept as null.
- **An open trade saves.** Exit and result are both optional and independent. A trade with no exit is simply still running: `realizedR` is null, so Phase 2's selectors skip it for net R and expectancy while it still counts toward win rate if a result was set. That asymmetry is deliberate and was confirmed in Phase 2.
- **`result` is auto-suggested from the exit's sign, then locked.** Once the trader picks a result by hand, a `resultTouched` flag stops the suggestion from ever overwriting it again — including on later exit edits. **Adjustment requested by the user**, and the reason is sound: the app must never silently overrule a judgement the trader has already made.
- **Blocking stops where the database stops**: stop ≠ entry, range high > low, size > 0, and unparseable numbers. Everything softer is a warning rendered under the form that never disables the save — target on the same side of entry as the stop, entry outside the range, off-plan, a retired model, a result that disagrees with the exit, and drawdown within 2 points of the limit. **A future-set date was dropped from the warning list at the user's request**: it's a rare slip, and a form that cries wolf gets all its warnings ignored.
- **Sweep side is derived from the stop, with an override.** `deriveSweepSide`: stop below the range low → low purged, above the high → high purged, inside → no sweep. README says it's "inferred from which extreme was purged" but never from what; the Playbook's own C2 rule 4 ("Stop beyond the sweep wick") does. Verified against the mock's own numbers — stop 23,396.50 against a 23,402.75 low derives "low", exactly the "Low purged" the mock prints. `both` is unreachable by inference, so the panel offers an explicit override.
- **`size` stays required and is record-keeping only.** It feeds no calculation (`pnlAmount` is `realizedR × rValueAtEntry`), but the column is already NOT NULL, a journal entry without position size is half a record, and it's known the moment the order is placed. Labelled in lots, since the confirmed instrument set is 28 FX pairs plus XAUUSD.
- **`rValueAtEntry` is computed, read-only, and recomputed server-side on submit.** The form shows "1R today · $X — frozen onto this trade when you log it"; the value the row actually stores is recalculated in the server action from the account and its ledger, never taken from the client. Hand-editing it is deliberately impossible: it would break the invariant the whole Capital screen rests on and silently desync money from R. (Phase 6's CSV import will need a per-row value, since historical trades' 1R can't be derived from today's balance — flagged for then.)
- **No account → a first-run setup sheet, not a guessed default.** `accounts` was genuinely empty, and `trades.account_id`/`r_value_at_entry` are both NOT NULL, so this is the real first-run path rather than an edge case. Auto-creating an account with an invented starting capital was rejected outright — that number drives every figure on the Capital screen. The sheet asks only what a trade needs (name, starting capital, risk %, drawdown limit), previews the resulting 1R, and Phase 8's Capital screen will edit this same row rather than create a competing one. Closing it returns to the dashboard.
- **Models select stays optional** with a "No models yet — add them in Playbook" empty state; trades without a model group under "Unassigned", which Phase 2's `byModel` already handles.

Verified end to end against the mock's own trade in a real browser: range size 83.50, sweep side "Low purged", 50% level 23,444.50, R:R "1 : 5.2R" and realized "+2.8R" all match mock 1b/2b exactly. Then checked the two paths that matter most — a closed trade stored `r_value_at_entry` 150 (15,000 × 1%), and a second, open trade stored exit and result as NULL with `r_value_at_entry` 154.22, correctly recomputed from the balance the first trade had moved. Test account and user deleted afterwards.

**Two bugs in the Phase 3 `Modal` primitive that only real interaction exposed**, both invisible to build/lint/tsc and to the Phase 3 gallery check:

- **Focus theft ate keystrokes.** `Modal`'s setup effect listed `onClose` in its dependencies, and every caller passes an inline arrow, so the effect re-ran on every parent render and called `panelRef.current.focus()` — pulling focus out of whatever field was being typed into. Only the first character of any input inside a modal survived. Fixed by holding `onClose` in a ref so the effect depends on `open` alone.
- **The portal broke hydration.** `Modal` guarded its portal with `typeof document === "undefined"`, so the server rendered nothing while the client rendered the portal on its very first pass — a mismatch that made React discard and rebuild the subtree, wiping typed-in state with it. Fixed with a `mounted` flag so both first renders agree on null. The gallery never caught this because its modal only opens after hydration; the account gate renders open on first paint, which exposed it immediately.

## Phase 4b — draft autosave + attachment upload

Two questions were put to the user before building; both confirmed, with the debounce shortened from the original 3s proposal to 1.5s per the user's own reasoning (a draft write is cheap; the risk of losing the last few typed characters to a closed tab isn't worth trading for a slightly quieter network tab).

**Draft autosave.** Field edits debounce 1.5s after the last keystroke; attachment adds/removes bypass the debounce and save immediately (losing track of an upload is worse than an extra write). `docs/README.md` and `docs/build-prompt.md` both already say "restore on return", not "ask" — implemented as a silent, automatic restore, with the header showing "Draft restored · HH:mm" once (reusing the mock's own "Draft saved · HH:mm" slot and format) so the trader knows it wasn't a blank form, without a confirmation dialog. The draft is deleted on a successful trade save; closing the form without saving leaves it in place for next time, per spec. One judgement call not asked about: a **restored** draft starts with `resultTouched` already `true`, since there's no way to know whether the trader had manually set Result in the prior session — treating it as already-decided is the safer default, matching the same "never overwrite a deliberate choice" reasoning behind the touched-lock itself.

**Attachments — the orphan-file lifecycle.** `attachments.trade_id` is NOT NULL, so a DB row can't exist before a trade does, and `drafts` has exactly one row per user (`user_id` is the PK), which is what makes the whole design tractable:

- Uploads land immediately in one fixed temp folder, `{user_id}/drafts/`, direct from the browser to Storage (not proxied through a Server Action, so large files don't round-trip its body) — matching the "restore on return" promise for images too, not just text fields. The draft's `payload.attachmentPaths` is the list of what's there.
- Removing a thumbnail deletes the Storage object immediately and updates the draft.
- On a successful trade save, every draft-listed path is moved (`storage.move`, an atomic rename — nothing left behind to clean up) to `{user_id}/{tradeId}/{filename}`, an `attachments` row is inserted per file, and the draft is deleted. Best-effort per file: one failed move doesn't roll back the trade that already saved.
- **Reconciliation runs once per New Trade page load**: anything in the draft folder the current draft doesn't reference gets deleted. Not a cron job — since there's only ever one draft per user, the next visit to this page is always a safe moment to check. This is the closest thing to a guarantee against orphans without standing infrastructure: the only real gap is a trader who uploads to a draft and then never opens New Trade again, ever — accepted as a fine edge case for a single-user personal app, flagged in the original proposal.
- Limits (none given in the spec, proposed and confirmed): PNG/JPEG/WebP, 8MB per file, 6 per trade. Client-side validation gates the picker; the server re-checks all three independently, since a client-side cap is trivially bypassable.

**Verified against the live project in a browser, not just re-read from the code** — every step below was checked against the actual database/Storage state, not just the UI:
- Filled fields, waited past the debounce, confirmed `drafts.payload` held the typed values and `updated_at` matched the header's timestamp; reloaded the page and confirmed both the fields and the header ("Draft restored · HH:mm") came back.
- Uploaded a real (in-page-generated) PNG through the actual file input: confirmed it landed at `{user_id}/drafts/{generated-name}.png` in Storage and the draft's `attachmentPaths` updated immediately, ahead of the debounce.
- Manually planted an orphan object in the same user's draft folder (a file the draft didn't reference), reloaded the page, and confirmed the orphan was deleted while the referenced file survived untouched.
- Removed an attachment from the form and confirmed both the Storage object and the draft's path list were gone.
- Logged a trade with an attachment and confirmed: the `attachments` row pointed at the final `{user_id}/{tradeId}/{filename}` path, the file existed there and *nowhere else* (no leftover at the draft path — the move was genuinely atomic), and the `drafts` row was gone.
- All test data (a disposable account, trade, attachment, and draft) was created under a throwaway auth user and fully deleted afterward — the user's own account, trade, and settings were read but never modified.

**Noted, not fixed (out of scope for this task):** `formatPrice` is fixed at 2 decimal places, so an FX pair's range size (e.g. 1.2650 − 1.2600 = 0.0050) displays as "0.00" instead of a useful value. This predates Phase 4b (it's the same helper used for the index/futures-style prices in the mocks, which don't need more precision) and only surfaced now while testing with a real FX instrument. Flagged for whichever phase next touches price formatting.

## Phase 4 follow-up — instrument-aware price/pip formatting (was deferred above, fixed before 4c)

The user rejected deferring this: every one of the 28 instrument presets is an FX pair, so a fixed 2-decimal `formatPrice` made every price and range-size figure on the New trade screen meaningless. Fixed as a display-layer-only change — the domain layer (`rangeSize` etc.) keeps full float precision; nothing here rounds before the value is stored.

- **Decimal precision is instrument-aware, not global.** `src/lib/instruments.ts` adds `isJpyPair` (`instrument.trim().toUpperCase().endsWith("JPY")`), `priceDecimals` (3 for JPY pairs, 5 for everything else), and `pipSize` (0.01 vs 0.0001). This app is FX-only by design (metals were already dropped in the Phase 4a instrument-list decision above), so there's no third "unknown instrument" bucket to design for — the two-way split covers every preset and every free-typed pair as long as it's shaped like an FX symbol ending in the quote currency.
- **`formatPrice(value, instrument)`** now takes the instrument and looks up its decimals instead of hardcoding 2. Used for the three absolute prices in the range diagram (Low / 50% / High captions).
- **Range size switches to pips, not raw decimal.** The user's own framing — "0.0050 is harder to read than 5.0 pips" — was confirmed directly: a new `formatPips(value, instrument)` divides the difference by the instrument's pip size and returns one decimal place (e.g. "50.0", "0.5"). The caller wraps it in the usual `useT` label (`"50.0 pips"` / `"50.0핍"`), matching how every other unit label in this app is localized rather than baked into the formatter.
- **Verified live**, not just unit-tested: created a disposable test user, logged into the actual New Trade form, entered a EURUSD range (1.2605–1.2655) and confirmed the diagram read "Low 1.26050 / 50% 1.26300 / High 1.26550" with "Range size 50.0 pips" (not "0.01" or "0.0050"). Logged the USDJPY trade and confirmed via a direct `psql` query against the live database that the stored `range_high`/`range_low`/`entry`/`stop` kept full precision (`1.2655`, `1.2605`, `156.325`, `156.275`) — proving the fix never touched what gets persisted. ## Phase 4c follow-up — three usability fixes reported after real use

The user hit all three while actually using the app on their own account (not synthetic testing), which is exactly the kind of bug real usage surfaces that a form built against one demo trade doesn't.

**1. Combobox always filtered by the current value.** `Combobox` computed its dropdown list by filtering `options` against the field's own current value on every render, so once the field already held a valid preset (e.g. "EURUSD"), opening the dropdown showed exactly one match — switching pairs meant deleting the text first. Fixed by splitting "the list is open" from "the user is actively filtering it": opening the field (focus, arrow key) now always shows the full unfiltered list with the current value's row scrolled into view and highlighted (`open()` in `combobox.tsx`, tracked via a new `isFiltering` state that starts `false` and only flips `true` from the input's own `onChange`, i.e. the user actually typing a character). The `.slice(0, 8)` cap on the list was also dropped — the dropdown already scrolls (`max-h-[264px] overflow-y-auto`), and the full preset list is only 28 items, so there's no reason to hide the rest of it.

**2. Clipboard paste for attachments.** TradingView's own chart-capture puts an image directly on the clipboard; round-tripping through Save-to-file → Choose file just to get it into a trade was the actual friction reported. Added `usePasteAttachment` (`src/lib/use-paste-attachment.ts`), a small hook that listens for a `paste` event at `window` — not scoped to the dropzone having focus, since after alt-tabbing back from another app whatever last had focus on the page is unpredictable — and only acts when the clipboard actually contains an image (`item.type.startsWith("image/")`), so it never interferes with an ordinary text paste into some other field on the same page. Wired into all three places a screenshot can be added: the New trade form, Trade detail's edit form, and Trade detail's own Charts-card "Add" (view mode). Each Dropzone's hint copy now mentions "paste with ⌘V"; the Charts card additionally keeps a small persistent caption once it already has attachments and its Dropzone (empty-state only) has disappeared, so the capability stays discoverable either way.

**3. A price wildly outside an instrument's normal range now warns.** The user pasted an index-style price (23,411) into a EURUSD field and got a mathematically-correct-but-meaningless "835000.0 pips" range size — the numbers were right, the input was wrong. Judged worth a warning (the user explicitly left this call open — "과하다고 보면 안 해도 된다") rather than skipping it, since it's the same class of mistake `result_disagrees_with_exit` already exists to catch, and it's cheap to check. Not a data table of 28 real historical per-pair ranges — a coarse "is this even the right order of magnitude" bound is all that's needed to catch a mistake four orders of magnitude off, without flagging anything merely unusual: `isPlausibleFxPrice` (`src/lib/instruments.ts`) uses `[0.2, 5]` for standard pairs and `[20, 500]` for JPY pairs (JPY sits ~2 orders of magnitude higher, same split as the existing decimal-precision rule), comfortably wide of every real modern-era major/cross. A new `price_implausible_for_instrument` warning in `collectWarnings` fires if any of rangeHigh/rangeLow/entry/stop/target/exit falls outside that band for the trade's instrument — non-blocking, like every other warning in this app.

**`collectWarnings`'s `WarningInput` gained an `instrument` field** (both the New trade form and Trade detail's edit form already had it in scope, so this was a one-line call-site change in each).

**Live verification hit a real obstacle, worked around without touching real data**: the browser session already had the user's own account signed in (no "Set up your account" gate, and — tellingly — the very draft that reproduced their reported bug, complete with the "835000.0 pips" figure). `document.cookie` is blocked from JS for this session and a direct `psql` read of `accounts` was blocked by the permission classifier, so there was no safe way to confirm identity except by what rendered; closing the Chrome window didn't clear the session either (Supabase's auth cookie is long-lived, not tied to browser-process lifetime). Rather than risk writing to the real account, verification split three ways:
- Combobox (fix 1) and the price warning (fix 3) were confirmed **read-only, against that same real draft** — opening the Instrument dropdown and scrolling to check the warning card never mutates anything, so this was safe and also happened to be a direct live confirmation of the exact reported bug.
- The scroll-to-selected-option behavior specifically (harder to see with EURUSD, which already sits first in the list) was confirmed separately on `/dev/components`, which is pure client-side demo state with no Supabase calls at all regardless of who's signed in — set the combobox to NZDCHF (near the bottom of the 28-item list), closed it, reopened it, and confirmed it jumped straight back to NZDCHF's row rather than the top.
- **Clipboard paste (fix 2) was not exercised live** — every avenue to get a clean disposable-user session was blocked or unavailable (cookies unreadable, DB read blocked, no logout route exists yet, and closing the browser window didn't end the session). It reuses the exact same `addFiles` path already end-to-end verified in Phase 4b/4c (upload → Storage → DB row → signed-URL preview); the only new code is the clipboard-to-`File[]` extraction in `usePasteAttachment`, which is straightforward enough to review by reading rather than requiring a live upload to trust. Flagged here rather than silently claimed as verified — worth a 10-second manual spot check (copy a screenshot, ⌘V on the New trade or Trade detail Charts card) whenever convenient.

The user confirmed paste itself works and reported the actual bug: thumbnails rendered at the pasted image's original aspect ratio, stacked vertically below the dropzone — a tall narrow sliver of a landscape TradingView capture, unrecognizable as a chart.

## Phase 4c follow-up — one shared attachment thumbnail component, replacing two different broken ones

There were, it turned out, two different thumbnail treatments already in place, and neither was right:

- **New trade form + Trade detail's edit form** used a `grid-cols-3` grid of `aspect-square` tiles. Square should have worked (`object-cover` crops to fill), but a landscape screenshot cropped to a square still throws away most of a chart's horizontal detail — recognizable, but not by much.
- **Trade detail's view-mode Charts card** followed `docs/README.md`'s own mock spec literally: 150px-tall, full-card-width slots stacked one per row (`flex-col`). ## Phase 6 — Trade log

Filtering/sorting/pagination is one new pure module, `src/lib/domain/trade-log.ts`, over the account's full trade list — same architecture as `stats.ts`'s selectors, so the table, the summary row, and CSV export all derive from the exact same functions rather than three slightly-different implementations. The route is fully server-driven: `src/app/trades/page.tsx` parses `?from=&to=&instrument=&session=&model=&sweep=&result=&offPlan=&sort=&dir=&page=` from the URL, fetches every trade for the account once (`getAllTrades`, no date-scoping — filtering is a client concern now, not a query concern), and does the filter → sort → paginate pipeline server-side before handing the client component only the current page's rows plus the pre-computed summary. Every filter pill, sort-header click, and pager button is a plain `router.push` to a new `?`-string built by `buildTradeLogSearchParams` — no client-side re-filtering of an already-fetched list, so the URL is genuinely the only state, matching README's "filter state lives in the URL" requirement exactly rather than approximately.

- **Page size is 20, not the mock's illustrative 5** ("Showing 5 of 18" in the canvas is clearly a small sample screenshot, not a spec) — chosen as a plain, ordinary table page size; nothing in README ties a number to it.
- **`sweepAlignment`'s cousin problem, solved the same way New trade already solved the model-name-vs-relative-magnitude question**: this screen's Session/Model/Sweep/Result filters are genuinely independent single-or-multi-select dimensions, so one new shared component, `FilterDropdown` (`src/app/trades/filter-dropdown.tsx`), covers all four rather than four bespoke controls — a `multiple` prop is the only thing that differs between "Instrument/Session/Model" (checkbox list, closes only on blur) and "Sweep side/Result" (single pick, closes immediately on selection). Closes via the same blur-timeout convention `Combobox` already established in Phase 1/3, not a new document-click-outside listener.
- **A fresh sort click defaults direction per column, not globally**: text-shaped columns (Instrument/Model/Session/Sweep) start ascending, date/Planned/Result start descending — a plain client-side judgment call (not URL-encoded as a "default"; `buildTradeLogSearchParams` still omits `dir` only when it equals the one global default, `desc`), matching the ordinary expectation that clicking "INSTRUMENT" for the first time shows A→Z, not Z→A.
- **Model sort/filter treats `null` (no model) as "Unassigned"** the same way Dashboard's Performance-by-model card already does, sorting as an empty string (first, ascending) — consistent rather than inventing a second convention for the same concept.
- **CSV export is a Route Handler (`src/app/trades/export/route.ts`), not a client-side blob download.** It re-derives the filtered set from the *same* query string the page itself reads (`parseTradeLogFilters`/`parseTradeLogSort` again, no pagination applied) rather than shipping the client an unpaginated trade list just so a button has something to serialize — the "Export CSV" control is a plain `<a href="/trades/export?...">`, and the browser's own download handling does the rest. Columns mirror Import's own field list exactly (enum-like columns write the English label, e.g. "Low purged", not the raw code) plus two derived, non-importable columns (Planned R, Realized R) appended for a human reading the file — Import's own mapping step ignores any column it has no field for, so the extra columns don't confuse a straight export-then-reimport round trip.
- **CSV parsing is 60 lines of hand-written RFC 4180, not a dependency** (`src/lib/csv.ts`) — quoted fields, doubled-quote escaping, embedded commas/newlines, all unit-tested directly. In line with this codebase's running preference (`clsx`/`tailwind-merge` were the one prior exception, added only because merging conflicting Tailwind classes correctly isn't reasonably hand-rollable) for writing a small, correct, testable piece over a new dependency when the grammar is this contained.
- **Import's column-mapping step is required precisely for `CSV_REQUIRED_FIELDS`** (the same NOT-NULL set Phase 4a already established for the New trade form, plus `rValueAtEntry`) and optional for everything else; a best-effort `guessMapping` pre-fills any column whose header matches a target field's key or either locale's label, but never blocks on a miss — the user confirms or fixes every mapping before the mapped rows are ever parsed.
- **`rValueAtEntry` is read directly off the CSV row, never recomputed** — the one deliberate divergence from `createTrade`'s own behavior, and exactly what docs/decisions.md flagged back in Phase 4a: "Phase 6's CSV import will need a per-row value, since historical trades' 1R can't be derived from today's balance." A row missing it, or with a non-positive value, is rejected in the preview step like any other invalid row.
- **A model name that doesn't match any existing model is treated as Unassigned, not a rejection** — a typo'd or since-renamed Playbook entry in someone's historical CSV shouldn't sink an otherwise-valid row over one non-critical field.
- **Enum-like columns (Direction/Session/HTF pairing/Sweep side/Result) accept either the raw stored code or either locale's display label**, via the same `resolveLabel` helper Trade log's own filter dropdowns use nowhere near as forgivingly — reused here specifically because a hand-authored or spreadsheet-exported CSV is far more likely to contain "Long"/"롱" than the internal code `long`.
- **A real bug, found by actually importing a CSV rather than only unit-testing the schema in isolation**: every row using an HTF pairing written as "W -> 2D" (a plain ASCII arrow, which is what any spreadsheet or hand-typed CSV will actually contain) was rejected as "Unrecognized HTF pairing", because `resolveLabel` did a literal string compare against `HTF_PAIRING_LABELS`' stored "W → 2D" (the real "→" glyph). Fixed by normalizing both sides of the comparison — collapsing `->` to `→` and squashing surrounding whitespace — inside `resolveLabel` itself (`src/lib/labels.ts`) rather than only in the CSV path, since the normalization is inert for every other label set (none of them contain an arrow) and this way Direction/Session/Sweep/Result/HTF pairing all benefit from the same leniency by construction instead of three of the five getting it and HTF pairing needing a special case. Caught live: a hand-built test CSV with three realistic rows and one deliberately-broken row initially came back "0 ready to import, 4 rejected" — all three good rows failing on the HTF pairing column specifically, not the deliberately-bad row, which was the tell that something systematic (not row-specific) was wrong.

- **Dashboard and mobile home's "View all N" / "전체보기" links, previously inert placeholders** (Phase 5, before Trade log existed to link to), now route to `/trades` pre-filtered to the same period each card already summarizes — the desktop card's current calendar month (`from`/`to` from `monthRange`), the mobile "오늘" card's exact day (`from = to = today`) — reusing `buildTradeLogSearchParams` rather than hand-building a query string a second way.

## Phase 7 — Playbook + Weekly review

**Weekly review's schema already existed, unused, since Phase 0** — `weekly_reviews` (iso_week, what_worked, what_didnt, one_change, focus_items jsonb) was created in the very first migration but nothing had read or written it until now. It already matches the mock's real shape exactly (three separate text columns, not the single "text" field README's own State Management section sketches) — no migration needed this phase.

**Weeks are ISO 8601** (`YYYY-Www`, Monday-start, week 1 = the week containing the year's first Thursday), hand-rolled in `src/lib/domain/weekly-review.ts` since JS has no built-in ISO week support. Verified against the mock's own numbers before trusting it: Sep 9 2026 → `2026-W37`, and that week's range → Sep 7–13, both exact matches. Some ISO years have 53 weeks and some have 52 (2025 has 52) — worth noting since it's an easy thing to assume incorrectly when writing the tests for `shiftIsoWeek`.

**Playbook**

- **One accordion, `expandedId` state, defaulting to the first model** — matches the mock's own framing ("First card is the expanded model") rather than defaulting to nothing expanded.
- **Every field is inline-editable with no separate edit mode**: name and description are plain `<input>`/`<textarea>` sitting directly in the display layout (transparent background until hovered/focused, then the field affordance appears), saving on blur. Rules are the same pattern per line, plus add/remove buttons. This matches "rule lists are editable in place" literally rather than building a pencil-icon edit toggle the mock never shows.
- **A new model starts as literally "New model", empty, active, appended after every existing one** (`sortOrder = max + 1) — there's no separate "create" dialog to keep in sync with the inline-editing surface; renaming and adding rules immediately after creation is the same interaction as editing any other model.
- **Retiring/reactivating is immediate, no confirmation modal** — unlike deleting a trade (Phase 4c), this never destroys data; it's a reversible status flag with an immediate "Reactivate" escape hatch right next to it, so the safety bar that applies to irreversible actions doesn't apply here.
- **The one-line retired notice is systematic, not the model's own free-text description.** The mock's own retired example (`"Mid-range entry"`) happens to have a description that already explains the off-plan consequence, but that's the *user's* free text, not something to rely on — a model retired without rewriting its description would otherwise show no such explanation at all. Added a fixed, always-shown caption for `status === 'retired'` (both the collapsed row and the expanded card) instead, independent of whatever the description field says: "existing trades keep their record as logged; only new trades matching this model are flagged off-plan."
- **Retiring doesn't touch a single trade row, by construction, not by care** — `offPlan` is recomputed fresh from each trade's own stored fields on every read (docs/decisions.md § Phase 2), so there is no code path that could retroactively flip a historical trade's status even if it tried to. The action's own doc comment says so explicitly, since this is exactly the kind of invariant worth being loud about at the one place someone might think to "fix" it later.
- **No reordering UI.** The mock draws no drag handle or up/down control anywhere, and "the dashboard's model breakdown reads its order from here" only requires that *an* order exists and Dashboard respects it (already true — `byModel` sorts by `sortOrder`) — not that Playbook itself expose a way to change it after creation. Flagged here rather than silently scoped out.
- Two mock values fall outside this project's own closed design-token scales: the rule-number/checkbox badge's "radius-6" (not in README's own radius list, but used identically in two independent mock sections — Playbook's rule numbers and Weekly review's focus checkboxes — real repeated intent, so added as a genuine new `--radius-6` token rather than rounding up) and its "10px" numeral text (a single, one-off occurrence with no repeat elsewhere, rounded up to this project's existing `text-11`, the smallest step in `FONT_SIZES`, per the same reasoning Phase 3 already used for the invented 28px stat-card size). Caught both by cross-checking every new utility class against `src/lib/cn.ts`'s `FONT_SIZES` array and the theme's `--radius-*` tokens before running anything — the same self-check discipline `text-36` and `rounded-4` were caught with in earlier phases, not a build-time guarantee (Tailwind silently emits no CSS for either kind of miss).

**Weekly review**

- **"Vs. 4-week avg" is the mean net R per calendar week over the 4 ISO weeks immediately before the one being viewed**, treating a week with zero realized trades as 0 rather than excluding it from the average — an average "per week you actually traded" would flatter a habit of skipping weeks. The mock's own "+2.1R" / "avg +5.1R" pairing is read as (this week's net) − (prior average) for the headline figure, with the average itself as the sub-line.
- **Tag frequency's bar share is count ÷ that week's total trade count, not count ÷ the top tag's count** — reverse-engineered from the mock's own numbers: a week of 9 trades with tag counts 8/4/2/1 renders bar widths 89%/44%/22%/11%, which only lines up against 9 (the trade count), not 8 (the top tag) where the top bar would need to read 100%. The "weak" (grey) vs. full-ink threshold reproduces the same example exactly at "count < half of the top tag's count."
- **Focus items carry over by dropping the checked ones and keeping the rest, computed once at first view of a new week, not on every render.** `getOrCreateWeeklyReview` (`src/app/weekly-review/get-or-create.ts`) checks for an existing row first; only if the week has never been opened does it look at the previous week's row and seed `focus_items` with `carryOverFocusItems(previous.focusItems)` on insert. Opening the same week again later just reads the row as it now stands (including anything since checked off or added) — carry-over is a one-time seeding event per week, not a live merge that would fight the user's own edits.
- **"Copy last week's notes" needed no extra fetch** — the previous week's review was already being loaded to compute carry-over, so `getOrCreateWeeklyReview` returns it alongside the current week's row and the button just copies its three text fields into local (unsaved) textarea state, letting the user edit before committing with "Save review."
- **The three review textareas save only on the explicit "Save review" button; the checklist and its additions/removals save immediately on each interaction.** Matches the mock's own two different affordances for these — a persistent checklist that's always "live" versus a page-length editorial pass a trader closes out deliberately — rather than picking one autosave convention for both.
- **Not one of the five `NAV_ROUTES` destinations** — the mock's own turn-list frames it as reached from the Dashboard, not as a persistent nav tab, and README's Nav section only ever lists "Dashboard / Trades / Calendar / Playbook" as routes. Reachable via a plain "Weekly review" link added to the Dashboard's own header (both desktop's `TopBar` right slot and mobile home's top area) instead of inventing a sixth primary destination. `TopBar`/`BottomTabBar` render with no item marked active on this page (`activeHref=""`, matching nothing) rather than falsely highlighting Dashboard.
